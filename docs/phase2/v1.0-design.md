# V1.0 Design review: rigid molecules from XYZ

**Status: draft for review, revised after round 66 (2026-11-18).**

This is the pre-implementation review that plan §8 requires. The approved proposal
(`docs/phase2-proposal.md`) makes it the gate before V1.1. It covers:

- the observable and parameter schemas;
- the inference assumptions;
- resource budgets;
- the D19 outputs;
- snapshots, hashes and journal replay;
- the contract.

It records the two early decisions the proposal asks for: how old torsion-less drafts are read,
and replay across numerical contexts. It changes no code.

**Scope, as approved:**

- fixed geometry;
- an achiral, uniaxial medium;
- the point groups C1, Cs, C2v, D2h, D3h and D6h;
- no fast internal motions;
- per-atom isotope identity;
- ¹H–¹H observations.

**What changed after round 66.** The first draft wrote each project at the lowest schema version
that could express it, and scoped the numerical context to the features a project used. Round
66 showed that this breaks the journal's rules as soon as one history mixes versions: through
undo, through a proposal that replaces the project several times, in snapshots, and in jobs
that finish after an undo. **This revision instead migrates once, completely** (D-1). After the
migration, a project directory has one schema and one numerical context.

## 1. What exists, verified in the code (round 66 confirmed, with the qualifications below)

- **Project files are strict.** `Wire` models forbid extra fields. `schema_version` is
  `Literal[2]`. `migrate_project` upgrades stored payloads one version at a time.
  - The standalone `.dipolar.json` loader (`formats.py`) checks the version with its own message
    before migration runs.
- **The journal** stores a `project_schema` per record, and `_record_schema` checks it:
  - the version never decreases;
  - every `project.replaced` event in a record carries the same version.

  Old payloads are migrated as they are replayed. v1 → v2 already works this way.
- **Identity.**
  - `science_hash` is the SHA-256 of `{numerical_context(), project}`.
  - `content_hash` is the same without `next_coupling_id`.
  - Both use the **live** context, and so do `payload_hash` and `job_ops.input_hash`.
- **Replay.**
  - Replay refuses a record whose stored context differs from the live one.
  - Snapshot loading refuses a snapshot whose context differs.
  - So adding a key to the context makes every journal **that has records**, and every
    snapshot, unreadable. An empty journal has nothing to compare.
- **Staleness** compares `content_hash` when it is known, and falls back to `science_hash`.
- **Jobs.** The worker receives the project JSON captured at submission. The durable job record
  stores the input *identities* (hashes) and options, not the project itself.
- **Snapshots** hold the whole session state: the project, view, undo and redo stacks,
  proposals, jobs, runs, ID counters and the request table, with schema versions, the context
  and a checksum.
- **Imported geometry.**
  - An atom is `(element, x, y, z)`. XYZ elements are H, D, C, N, O, F, P, S, Cl, Br and I.
  - Only `H` atoms become spins (¹H). `D` is kept as an atom and is not a spin.
  - `torsion` is optional. A project without one is a draft that cannot be fitted.
- **`ModelSpec`** is `(kind ∈ {rigid, jump4}, order ∈ {bisector-diagonal, c2z, c1}, frame,
  phi_domain_deg)`.
  - `model.set` takes a unit-bearing `phi_domain`.
  - `fit.run` returns a job submission.
- **`fit()` at k = 0** raises `ValueError` (zero-size reduction). The inner solve works.
- **`Problem`** accepts a full covariance (core only). The app builds problems from per-row σ.

## 2. Decisions

### D-1 One complete migration per project directory

When V1's application opens a project directory written by an earlier version, it migrates it
once, before serving. A migration is **a compaction across versions**, built on the existing
crash-safe rotation (snapshot `next` file, archive, rename).

1. **Replay under the old rules.** The legacy reader is today's code, kept as
   `dipolar_app.legacy.v2`. It loads the latest snapshot and replays the journal, with every
   hash and context check as written. A directory that does not verify is not migrated: it is
   reported as `JournalCorrupt` and left untouched.
2. **Migrate the whole state, purely.** `migrate_project` v2 → v3 is applied to the active
   project and to every project in the undo and redo stacks.
   - **Pending proposals** are expired, with the recorded reason `MIGRATED`. Their plans were
     built against v2 payloads.
   - **The request table** is kept: its fingerprints are of arguments, not projects.
3. **Map the runs.** During the legacy replay, every visited state's old science and content
   hashes are recorded beside the v3 hashes of its migrated project. Each run then keeps:
   - its **original** input identities, as historical provenance;
   - its **migrated** input identities, looked up in that map.

   A run whose input state cannot be reached (from before a snapshot whose archived journal the
   user deleted) gets no migrated identity. It is reported as **stale: input not recoverable
   after migration**: never as current.
4. **Write a v3 snapshot** under the v3 context, with a `migration` header:
   - the legacy final sequence number, science hash and context;
   - the archive file names;
   - the run map;
   - the code version.
5. **Archive** the v2 snapshot and journal (`archive/`), and start an empty journal.

**Result files and blobs** keep their bytes. Their headers keep the identities they were written
with, and the migrated identities live in the run records. **The standalone `.dipolar.json`
loader** migrates v1 and v2 files to v3 in memory; export writes v3.

**Why this design.** There is one encoder, one schema and one context for everything written
afterwards:
- a project payload is always v3;
- the journal checks never meet two versions in one record;
- a job's `input_hash` and its result use the single live context;
- staleness compares the migrated identities.

The legacy reader is used only by the migration, and stays as the audit path for the archive.

**Gates (V1.3).**
- A fixture directory of each shape migrates and then replays under the v3 rules:
  - a v2 journal only;
  - snapshot plus journal;
  - a crash left at each rotation step;
  - undo and redo stacks spanning a compaction;
  - pending proposals;
  - current runs, stale runs, and runs whose inputs are unrecoverable;
  - the allocator case: `content_hash` restored, `science_hash` not.
- Every run's status (current or stale) is the same before and after the migration, except the
  unrecoverable ones, which are stale.
- A migration interrupted at any step leaves the directory openable: either still v2, or fully
  v3.
- The archive still verifies under the legacy reader.
- Every Phase 1 test passes against migrated fixtures, and the biphenyl and 8CB φ-path numbers
  are unchanged.

### D-2 The numerical context

V1 adds global entries:
- `fixed_fit` (the k = 0 path's version);
- `rank_policy` (D-6);
- `symmetry_check` (D-4);
- `tensor_basis` (D-5);
- `feasibility_certificate` (D-7).

**After a migration there is one context.** No old record is ever replayed under the new one:
the migration replays it under the legacy reader. `_recorded_hash` and snapshot loading compare
against the single live context, as today. A later context change follows the same pattern: a
version bump plus a migration.

### D-3 Model states, and old drafts

A new model kind, **`fixed`**, keeps the existing meanings of `rigid` intact.

| State | Geometry | `model.kind` | `order` | `frame` | `phi_domain_deg` | Symmetry |
|---|---|---|---|---|---|---|
| Template fit (unchanged) | biphenyl template | rigid, jump4 | as today | bisector, ring-a | required | not allowed |
| Torsion fit (unchanged) | imported, torsion set | rigid | c2z, c1 | input | required | not allowed in V1 |
| **Draft** (unchanged) | imported, no torsion | rigid | as stored | input | as stored | optional |
| **Fixed-geometry fit** (new) | imported, no torsion | **fixed** | **point-group** | **symmetry** | **null** | **required** |

- **Old drafts (the early decision).** A v2 imported draft without a torsion migrates as a
  draft, keeping its stored domain. It becomes fittable only when the user:
  1. declares a symmetry (C1 means "no symmetry"), then
  2. sets `model.kind = fixed`.

  Readiness for a draft says:

  > "declare a torsion, or declare the molecule's symmetry and choose a fixed-geometry fit"

- **Transitions are atomic,** and validated the same way on load, direct edit, dry run and
  proposal acceptance:
  - `model.set` to `fixed` requires a symmetry and no torsion;
  - declaring a torsion while `fixed` is refused (`MODEL_CONFLICT`);
  - clearing the symmetry while `fixed` is refused (`MODEL_CONFLICT`);
  - leaving `fixed` restores `rigid` with a domain the user supplies.
- **`model.set` keeps its unit-bearing `phi_domain` argument.** For `fixed` the argument must be
  absent.

### D-4 Symmetry: the declaration, validation, the averaged geometry and orbits

**The declaration,** stored as `Molecule.symmetry`, holds:
- `point_group` ∈ {C1, Cs, C2v, D2h, D3h, D6h};
- `axes`: rows x, y, z in input coordinates, orthonormal and right-handed within 1e-9;
- `tolerance_a`: from 0.001 to 0.1 Å, default 0.01 Å;
- `medium`: `"achiral-uniaxial"`, the only value. A chiral medium is refused at the API
  (`MEDIUM_NOT_SUPPORTED`).

**The frame conventions** (the symmetry frame is the frame of S):

| Group | Convention |
|---|---|
| Cs | z normal to the mirror plane |
| C2v | z along the C2 axis; x and y in the two mirror planes |
| D2h | x, y, z along the three C2 axes |
| D3h | z along C3; x along one C2′ |
| D6h | z along C6; x along one C2′ |
| C1 | any frame |

C2, C2h and C3v are refused for new declarations (`POINT_GROUP_NOT_SUPPORTED`). The legacy
`c2z` order model stays valid on the torsion path.

**The origin.** Coordinates are centred at the **unweighted centroid of all atoms**. A symmetry
operation maps a symmetric molecule's atoms onto each other, so it fixes this centroid; a
translated XYZ file therefore validates.

**The group action.** Each group's operations are generated from standard generators in the
symmetry frame and closed into the full group table.

**Validation.** For each operation g, every centred atom x_i is matched with the unique atom j of
the **same element and mass number** nearest to g·x_i, within `tolerance_a`.
- **Refused:** two atoms of that kind within 2·`tolerance_a` of g·x_i (ambiguous), or no atom
  within `tolerance_a`. The message names the operation and the atom.
- **The matches must be a group action.** Each π_g must be a permutation, and π_gh = π_g ∘ π_h
  for every pair in the group table; otherwise the declaration is refused.

**The averaged geometry** is x*_i = |G|⁻¹ Σ_g g⁻¹ x_{π_g(i)}.
- Because the π_g form a group action, x* is exactly symmetric: g x*_i = x*_{π_g(i)}.
- The fit uses x*. The input coordinates stay stored, x* is derived (never journaled), and the
  largest displacement |x*_i − x_i| is reported.

**Orbits.**
- **Site orbits** and **unordered-pair orbits** come from the same π.
- An unordered pair maps to the sorted pair (π_g(a), π_g(b)), so both endpoints are permuted
  together.
- **One design row per pair orbit,** computed from the orbit's representative (the smallest pair
  of spin IDs). Equal predictions within an orbit hold by construction, not up to rounding.

**Equivalence.**
- Site orbits are *chemical* equivalence under the declared symmetry.
- *Magnetic* equivalence also needs the same resonance frequency and identical couplings to
  every other spin. It is never used to merge observations.
- In 1,4-dichlorobenzene, H2 and H6 are in one site orbit, but H2–H3 and H6–H3 are different pair
  orbits with different predicted couplings. Both are kept, and a test checks this.

### D-5 Couplings under a fixed-geometry model: one estimate per pair orbit

- **Every H atom must be a spin.** A loaded fixed-geometry project with an H atom that has no
  spin is refused. Orbits are complete by construction.
- **Rows are keyed by pair orbit.** The key is the orbit's representative pair of **spin IDs**,
  after label mapping.
  - Reconciliation (D5) matches existing rows by orbit key. Importing another member of an
    existing orbit is therefore an *update of that row*, keeping its coupling ID, not a remove
    and an add.
- **Two rows in one orbit are refused** ("repeat measurements of one pair orbit are not accepted
  in this release"). Nothing is dropped.
- **The orbit fields.**
  - `equivalent_pairs` and `multiplicity` are derived from the orbit.
  - In the CSV, an *omitted* `multiplicity` or class is filled in; an *explicit* one must match
    the orbit, compared as unordered sets, or the import is refused with the difference.
  - The CSV parser therefore keeps "omitted" distinct from "1".
- **Edits that change the orbits are refused while rows exist** (`OBSERVATIONS_CONFLICT`, listing
  the rows that would merge or split). This covers a symmetry or isotope edit; the user resolves
  the rows first.
- **N counts rows**, never multiplicity.

### D-6 Isotopes

- **`Atom.mass_number: int | None`** (v3). Absent means the most abundant isotope.
- **Supported:**
  - `D` is the only spelling of deuterium; `H` with mass number 2 is refused;
  - ¹³C (C, 13) and ¹⁵N (N, 15);
  - an explicit default mass (C 12, N 14) is normalized to absent, so each identity has one
    spelling.
- **`molecule.set_isotope {atom, mass_number}`** applies to non-spin atoms only. Deuterating a
  proton means re-importing an XYZ file with `D`, since it removes a spin.
- **Validation.** An isotope edit is revalidated against the declared symmetry and the orbits
  (D-4, D-5), atomically.

### D-7 The order parameters: basis and reductions

**The orthonormal basis.** Internally, S is expressed in the coordinates (Frobenius norm,
Σ b_k² = tr S²):

b = (√(3/2)·S_zz, (S_xx − S_yy)/√2, √2·S_xy, √2·S_xz, √2·S_yz)

- Covariances, estimable functionals and rotation tests use b.
- The user-facing names (`Szz`, `Sxx-Syy`, …) map to b through a fixed linear map.

**The reductions.** With the frame conventions of D-4, the symmetry subspace has dimension d:

| Group | d | Free coordinates |
|---|---|---|
| D6h, D3h | 1 | b₁ |
| D2h, C2v | 2 | b₁, b₂ |
| Cs | 3 | b₁, b₂, b₃ |
| C1 | 5 | all |

**Fixed by symmetry.** Components that the symmetry sets to zero are reported separately, as
*fixed by symmetry*, not as estimated by the data.

**Rotations.** A frame change acts on b by an orthogonal 5 × 5 matrix R(Q). A test checks R(Q)
against `frame_change` for random rotations.

### D-8 The k = 0 fit: rank, estimands, intervals, adequacy

- **The estimate.** In the reduced coordinates (dimension d), the whitened design WA_d has the
  SVD U Σ Vᵀ. The cases N < d and s_max = 0 are defined:
  - with s_max = 0, nothing is estimable;
  - with N < d, the null space is completed with the full right singular basis.
- **Rank: required, then verified.** A singular value can only *diagnose* rank. Round 66 showed
  that a ratio near 1e-13 moves with the weights. So:
  - **The required rank r_req comes from the model.** It is d, reduced only by a **verified
    geometric degeneracy**, tested in Å on the averaged geometry and independent of the
    weights:
    - all observed pair vectors coplanar within 1e-6 Å: only the in-plane block can be seen;
    - all collinear within 1e-6 Å: only the component along the line;
    - k distinct pair directions (up to sign): at most k.

    r_req is the dimension of the symmetry subspace that each such degeneracy leaves visible. It
    is computed from the fixed basis matrices and the plane or line, never from the weighted
    design.
  - **The numerical rank r_num** is the number of singular values with s_i / s_max > 1e-10
    (`rank_rtol`, unchanged).
  - **The rank is verified** when r_num = r_req, with a margin: s_{r_req} / s_max ≥ 1e-6, and
    s_{r_req+1} / s_max ≤ 1e-10.
  - Otherwise the rank is **unverified**. The result says why: a weak direction, or a
    degeneracy not in the list.
- **Estimable functionals.**
  - A functional cᵀb is first mapped into the symmetry subspace.
  - It is reported as estimable when its relative projection error onto the retained directions
    is at most 1e-9: ‖(I − P)c‖ / ‖c‖. This test is scale-invariant.
  - Its estimate is cᵀb̂, with variance Σ_i (cᵀv_i)² / s_i².
  - When the rank is unverified, the estimate is labelled **approximate (restricted to the
    retained directions)**, with no exact interval.
- **Adequacy.**
  - χ² = ‖W(y − A b̂)‖², ν = N − r_req.
  - The p-value is given only when the rank is verified and ν > 0.
  - Withheld otherwise, with a code: `ADEQUACY_RANK_UNVERIFIED`, or `NO_DOF` when ν = 0.
  - A p-value below 0.001 flags the fit inadequate, as today.
- **What these statistics assume.** All of them are conditional on the stated σ and weights.
  Intervals for estimable functionals are exact under fixed geometry, Gaussian errors with known
  covariance (independent when σ is diagonal), and an unconstrained linear estimate.
  - Nothing is clipped to the physical region.
  - Principal values and axes have no intervals ("interval not supported: nonlinear").
- **Covariance in V1.** A full covariance stays core-only; the app supplies per-row σ, as today.
  The core refuses a covariance for N > 5000 *before allocating* it
  (`MAX_COVARIANCE_N`; about 200 MB as float64).

### D-9 Admissibility with certificates

The question: does the fitted family contain a physical tensor, that is, one with
λ_min(S) ≥ −1/2 (equivalent to (2S + I)/3 positive semidefinite, since tr S = 0)? The family
lives **inside the symmetry subspace**.

- **When r_req = d** (a fully determined fit, including D6h with d = 1), the fitted tensor is
  tested directly, as today.
- **When r_req < d,** the family is F = {S₀ + Σ_k c_k N_k}. The N_k are null directions within
  the symmetry subspace.
  - **Feasible:** a candidate S ∈ F with λ_min ≥ −1/2 − 1e-9, verified by an eigenvalue
    computation. This is the certificate, and it is shown as a *labelled representative*.
  - **Infeasible:** a dual certificate Z (3 × 3) with:
    - Z ⪰ 0 and tr Z = 1;
    - ⟨Z, N_k⟩ = 0 for every k;
    - ⟨Z, S₀⟩ < −1/2 − 1e-9.

    Weak duality then gives max_F λ_min ≤ ⟨Z, S₀⟩ < −1/2. Every condition is checked within
    1e-10.
  - **Undetermined:** neither certificate is verified. The search is never trusted on its own;
    only a verified certificate decides.
- **With an unverified rank,** the result concerns the retained projection only, and says so.
- **Tests:** boundary cases, repeated eigenvalues, two frames, and the round 65 rank-1 example.

### D-10 The result contract (D19)

- `fit.run` still returns a job submission.
- `run.get` returns a result with the discriminator **`model_kind: "fixed"`** and its own typed
  schema. Search-only fields (scan, basins, profiles, geometry parameters) are **absent**, not
  null. The fields:
  - `rank {required, numerical, verified, reason, singular_value_ratios}`;
  - `estimable [{direction_b, estimate, se}]`;
  - `components [{name, status: estimated | fixed-by-symmetry | unidentified, estimate?, se?}]`;
  - `adequacy {chi2, nu, p_value | null, status: given | withheld | no-dof | inadequate, code?}`;
  - `admissibility {status: admissible | inadmissible | feasible | infeasible | undetermined,
    representative?, certificate_summary}`;
  - `assumptions` (the text of D-8);
  - `symmetry {group, axes, tolerance_a, medium, max_displacement_a}`;
  - `orbits` (each row's orbit);
  - `warnings` (coded);
  - `provenance` (input identities, context, versions);
  - `estimand`: "order parameters of the fixed geometry, in the declared symmetry frame".
- `run.report` and the Fit workspace render this result.
- `fit.preview` and `fit.landscape` refuse a fixed model with `NO_TORSION`.

### D-11 The contract and the budgets

**The contract (D20).** New operations, a new model kind and a new result discriminator: a
**minor** version, with registry examples, the snapshot and Python/HTTP parity for each:
- `molecule.set_symmetry {point_group, axes, tolerance_a, medium}`, proposable, with a dry run;
- `molecule.set_isotope`.

Existing interfaces keep their shapes.

**The budgets.** Measured on named hardware in V1.1 and V1.2, recorded under
`docs/validation/data/`, and enforced by limits checked **before** any allocation. Each is
measured for the direct call, the dry run, proposal acceptance and the worker.

| Work | Limit | Budget to confirm |
|---|---|---|
| Symmetry validation | ≤ 1000 atoms, ≤ 24 operations | ≤ 1 s CPU, ≤ 200 MB |
| Orbit derivation | ≤ 100 000 rows | ≤ 2 s, linear memory |
| k = 0 fit | N ≤ 100 000, d ≤ 5 | ≤ 2 s, ≤ 100 MB |
| Certificates | ≤ 4 null directions | ≤ 0.1 s |
| Migration | at most the Phase 1 limits (snapshot every 5000 records) | measured; the project is not served until it completes |

## 3. Gates carried into the steps

**V1.1, the core fit:**
- frozen noiseless recovery for the rank-5, planar rank-3 and collinear rank-1 fixtures, each
  frozen by its required rank and its singular-value margins;
- a fixed-seed noisy regression, separate from the coverage test;
- coverage by the M1 protocol on the estimable components;
- R(Q) orthogonal, and rotated predictions and matched functionals equal (repeated singular
  values compared as subspaces);
- the rank cases:
  - verified;
  - unverified, from a weak direction;
  - unverified, from an unlisted degeneracy;
  - N < d;
  - s_max = 0;
- the certificate cases of D-9;
- the covariance cap refused before allocation;
- the φ path unchanged.

**V1.2, symmetry:**
- recovery and predictions for each supported group, including ideal benzene's single S_zz;
- a translated XYZ validates;
- refusals: a group the geometry lacks, an ambiguous match, a non-action, a chiral medium, an
  unsupported group;
- relabelling and joint endpoint permutation leave the fit unchanged;
- isotopes: benzene-d₁ refused as D6h and accepted as C2v; ¹³C splits an orbit;
- 1,4-dichlorobenzene's chemically equivalent but magnetically inequivalent pairs stay distinct;
- benzene's scale degeneracy;
- the budgets.

**V1.3, the application:**
- the D-1 migration fixtures and gates;
- the D-3 transitions and refusals on every path (load, edit, dry run, proposal);
- the D-5 orbit reconciliation (another orbit member updates the same row; repeats refused);
- standalone `.dipolar.json` v1, v2 and v3 load to the same normalized identity as replay;
- φ-free reports;
- registry, Python and HTTP parity.

**From the approved proposal:**
- the experimental criteria are preregistered (V0.3) before any experimental fit;
- when V1 code starts (after the beta exit, or with a `release/0.1` branch) is still the
  owner's decision, before V1.1.

## 4. Risks

- **The migration** is the largest new mechanism. It reuses the crash-safe compaction rotation
  and is gated by fixtures of every directory shape.
- **The dual certificate** needs a small dedicated solver (a 3 × 3 PSD variable). Without a
  verified certificate the answer is "undetermined", never a guess.
- **Symmetrization** moves atoms by up to `tolerance_a`. The result states the displacement and
  that it describes the averaged geometry.
